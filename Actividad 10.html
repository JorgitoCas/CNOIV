Practitioner

File Path Traversal (Double URL-Encoding Bypass)

Objetivo del Laboratorio

Evadir el filtro de secuencias utilizando doble codificación URL para leer el contenido de /etc/passwd.

2. Explicación Técnica de la Vulnerabilidad

Esta variante de Path Traversal se origina por una discrepancia en el orden de operaciones entre la validación de seguridad y la transformación de datos (Time-of-Check to Time-of-Use en el procesamiento de entradas). La aplicación bloquea o elimina secuencias ../ de la entrada del usuario, pero posteriormente realiza una decodificación URL adicional (superflua) antes de pasar la ruta a la API del sistema de archivos.

Catalogada dentro de OWASP Top 10 (A01: Broken Access Control / A03: Injection), esta falla vulnera directamente la Confidencialidad de la tríada CIA. Un atacante puede aplicar Doble Codificación URL (Double URL-Encoding) para que el servidor web decodifique la primera capa al recibir la petición HTTP, el filtro de seguridad evalúe la cadena aún codificada sin detectar el patrón ../, y finalmente la función superflua decodifique la segunda capa, reconstruyendo el salto de directorio hacia archivos críticos del sistema o credenciales de bases de datos.

3. Procedimiento Paso a Paso

Metodología técnica de intercepción, codificación y explotación en Burp Suite.

1

Intercepción del Tráfico HTTP

Se accede al laboratorio a través del navegador preconfigurado en Burp Suite. En la pestaña Proxy > HTTP history, se activan los filtros para visualizar las peticiones de imágenes y se selecciona una consulta GET hacia el endpoint /image?filename=18.jpg, enviándola al módulo Repeater.

2

Comprobación de Defensas Activas

Desde el Repeater se prueban los vectores anteriores: secuencias directas (../../../etc/passwd), secuencias anidadas (....//....//....//etc/passwd) y codificación URL simple (..%2f..%2f..%2fetc/passwd). Todas devuelven 400 Bad Request ("No such file"), confirmando que el servidor decodifica la entrada una vez y limpia de forma efectiva cualquier secuencia ../ visible.

3

Construcción e Inyección con Doble URL-Encode

Se codifica dos veces la barra diagonal (/ → %2f → %252f). Se reemplaza el valor del parámetro filename por la cadena ..%252f..%252f..%252fetc/passwd y se envía la petición modificada.

4

Obtención de /etc/passwd y Confirmación

Tras superar el filtro de limpieza gracias a la doble codificación, la función de decodificación superflua del backend interpreta los caracteres %2f como barras diagonales reales. El servidor responde con estado HTTP/2 200 OK mostrando las cuentas del sistema en texto plano y completando el laboratorio.

5. Explicación del Payload

..%252f..%252f..%252fetc/passwd

En formato hexadecimal ASCII, el signo de porcentaje (%) equivale a %25 y la barra diagonal (/) equivale a %2f. Al codificar doblemente la barra como %252f, engañamos el flujo de validación en tres etapas:

1. Envío: ..%252f..%252f..%252fetc/passwd
2. 1er Decode + Filtro: ..%2f..%2f..%2fetc/passwd
3. 2do Decode (Superfluo): ../../../etc/passwd

6. Mitigación Recomendada

Para erradicar vulnerabilidades derivadas de decodificaciones múltiples y filtros de secuencias, se deben aplicar los siguientes controles defensivos:

  • Decodificar antes de validar: Nunca ejecutar transformaciones o decodificaciones URL adicionales después de haber aplicado un filtro de seguridad.
  • Validación Estricta (Whitelisting): Validar que el parámetro contenga exclusivamente caracteres alfanuméricos permitidos o comparar contra una lista blanca de archivos existentes.
  • Canonicalización de Rutas: Resolver la ruta completa con APIs nativas del sistema (getCanonicalPath()) al final de todo procesamiento y verificar que el prefijo coincida con el directorio base esperado.
