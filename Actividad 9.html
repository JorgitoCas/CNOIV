File Path Traversal: Traversal sequences stripped non-recursively

Evasión de filtros de sanitización no recursivos mediante la inyección de secuencias de salto de directorio anidadas.

Acceder al Laboratorio Oficial en PortSwigger

1. Ficha Técnica del Laboratorio

Nombre del Laboratorio

Traversal sequences stripped non-recursively

Nivel de Dificultad

Practitioner

Tipo de Explotación

File Path Traversal (Filter Bypass por Anidación)

Objetivo del Laboratorio

Evadir la depuración no recursiva de secuencias ../ para extraer el archivo /etc/passwd.

2. Explicación Técnica de la Vulnerabilidad

Una defensa común pero defectuosa contra ataques de Path Traversal consiste en sanitizar la entrada del usuario eliminando las subcadenas de salto de directorio (../) antes de concatenar el parámetro con el directorio base del servidor. El fallo crítico ocurre cuando esta sustitución se aplica de forma no recursiva (en una sola pasada, por ejemplo mediante funciones simples como replace("../", "")).

Dentro del marco de OWASP Top 10 (A01: Broken Access Control), esta debilidad compromete directamente el pilar de Confidencialidad de la tríada CIA, permitiendo a un atacante reconstruir secuencias válidas tras la ejecución del filtro y leer archivos arbitrarios del sistema operativo o configuraciones de bases de datos a las que el usuario del servicio web tenga permisos de lectura.

3. Procedimiento Paso a Paso

Metodología aplicada mediante Burp Suite para interceptar, analizar y vulnerar el filtro del servidor.

1

Intercepción de Peticiones en Burp Suite

Se inicia el entorno del laboratorio utilizando el navegador integrado de Burp Suite. A través del módulo Proxy (HTTP History), se habilita la captura de tráfico para inspeccionar las peticiones GET generadas al cargar el catálogo de productos, identificando el endpoint vulnerable /image?filename=18.jpg.

2

Identificación del Filtro en Repeater

Se envía la petición capturada hacia la herramienta Repeater (Ctrl + R). Al probar vectores tradicionales como la ruta absoluta (/etc/passwd) o secuencias simples (../../../etc/passwd), el servidor responde con un error 400 Bad Request ("No such file"), confirmando que la aplicación exige partir del directorio local y elimina activamente las subcadenas ../.

3

Inyección de Secuencias Anidadas

Para evadir la limpieza no recursiva, se construye un payload con secuencias dobladas o anidadas. Se modifica el parámetro filename en el Repeater ingresando ....//....//....//etc/passwd y se transmite la consulta hacia el servidor.

4

Extracción de Datos y Resolución

El filtro del servidor elimina la secuencia interna ../ una sola vez, provocando que los caracteres restantes se unan y formen la ruta ../../../etc/passwd. El servidor responde con un código HTTP/2 200 OK desplegando todos los usuarios del sistema y marcando el laboratorio como resuelto.

4. Explicación del Payload

....//....//....//etc/passwd

El éxito de este payload radica en explotar la lógica de reemplazo lineal de cadenas. Cuando el backend ejecuta una instrucción equivalente a buscar y borrar ../ sin repetir el ciclo de validación:

1. Entrada: ....//....//....//etc/passwd
2. Filtro: Elimina la subcadena central "../"
3. Resultado: ../../../etc/passwd

5. Mitigación Recomendada

Depurar entradas eliminando secuencias conocidas es una práctica insegura propensa a evasiones. Para mitigar de raíz la vulnerabilidad se debe implementar:

  • Validación por Lista Blanca (Whitelisting): Verificar que el parámetro coincida estrictamente con una lista cerrada de nombres de archivo permitidos o utilizar identificadores numéricos mapeados en base de datos.
  • Canonicalización y Verificación de Ruta Base: Utilizar APIs como Path.GetFullPath() o getCanonicalPath() para resolver la ruta absoluta final y comprobar mediante código que comience estrictamente con el directorio público autorizado (ej. /var/www/images/).
